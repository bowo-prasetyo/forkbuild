# AI/ML features audit, 2026-10-28

A Senior AI/ML Engineer's audit of ForkBuild 1.5.0 (branch head of
2026-10-28). It asks one question: **are the AI/ML features coherent, and
are they in good shape?**

This is a review, not a decision record. [Pillars.md](../Pillars.md) still
wins, and whatever is adopted goes into the roadmap the usual way.

## What counts as AI/ML here

[Architecture.md](../Architecture.md) calls voice building "ForkBuild's one
real AI feature", and that is true of learned models. But seven features
make guesses from fuzzy input, and each one can be wrong in ways a player
notices, so this audit treats them as one intelligence layer:

| Feature | Technique | Where |
|---|---|---|
| Voice building | Whisper tiny (q8) on ONNX Runtime WebAssembly, in a worker; closed-vocabulary matching after it | `application/voice/`, `core/voice/`, `ui/voice/` |
| Look-alike hints (Publish, build page, 🔔, Explore) | Voxel-set Jaccard after rigid alignment by offset voting; ready-made structures taken out first | `core/catalog/BuildSimilarity.js`, `application/publication/SimilarBuildFinder.js`, `LookAlikeBuildNotifier.js` |
| Commands in plain words | Slot filling from per-language lexicons | `core/building/PlainCommand.js` |
| Help: Ask the guide | IDF-weighted lexical retrieval with fuzzy and bigram matching | `core/help/GuideSearch.js` |
| Build Library "finds what you describe" | Substring match, then lexicon word overlap | `core/library/LibrarySearch.js` |
| Describe the Build, Suggest a title, What changed | Exact facts turned into sentences from templates | `core/catalog/BuildDescription.js` |
| Blueprint similarity | Set similarity, as evidence | `core/building/BlueprintSimilarity.js` |

## How this was checked

- I read every file in the table, the voice and look-alike sections of
  Architecture.md, the 1.5 release notes, `scripts/vendor.mjs`,
  `scripts/pin-speech-model.mjs` and `scripts/evaluate-ready-made-detection.mjs`.
- I ran the related Node tests
  (`node tests/run.mjs Voice Speech Transcript Similar LookAlike PlainCommand GuideHelp LibrarySearch BuildDescription PinnedSpeech BlueprintSimilarity`):
  12 files, all pass.
- I measured `compareBuildShapes()` on made-up copies and coincidences, and
  `searchGuide()` against the real English guide with 16 questions a new
  player might ask. The numbers below come from those runs, not from
  reading the code. The scripts are in the appendix.
- I did not run Whisper. This container can't reach Hugging Face, and
  there is no recorded-speech test set to run it on (see finding 6).

## Verdict

**The architecture is coherent and the engineering discipline is unusually
high. The look-alike engine has correctness and robustness gaps that matter
now that it notifies other people. No feature is measured for accuracy
except ready-made detection.**

What is good, and should be kept:

- **Supply chain.** The engine and all seven model files are pinned by
  SHA-256 at one commit, cached copies are checked again, unpinned files
  are answered as missing without being fetched, and the CSP allows
  `'wasm-unsafe-eval'` but never `'unsafe-eval'`. Few production apps that
  run models in the browser do this well.
- **Privacy and isolation.** Inference runs on the device in a module
  worker, nothing is downloaded until the player agrees, and Remove
  deletes it.
- **Use of a small model.** Silence is cut and quiet voices are brought up
  before inference (`SpeechPreparation.js`), and silent clips never reach
  the model, so it can't make words up from them. The made-up sign-offs
  are filtered in all eight languages. Transcripts are matched to a closed
  set of commands with a margin, so the matcher abstains rather than
  guesses. This is the right way to get dependable commands out of Whisper
  tiny.
- **Bounded action space.** Voice reaches only Editor actions that Undo
  reverses, plus navigation in World View. It cannot reach Publish,
  sharing or anything else that leaves the device. A mishearing costs one
  Undo.
- **Honest framing.** Look-alikes are "a hint, never a finding", the
  device's limited view is stated, and ready-made structures are taken out
  so that shared Build Library content doesn't count as copying.
- **Docs match the code.** Every behaviour I checked in Architecture.md is
  what the code does.

## Findings

Ranked by severity. "Measured" means a number from the appendix scripts.

### 1. High: an exact copy of a regular build can score below the threshold

**Measured.** `compareBuildShapes(x, x)`, comparing a build with itself,
gave:

| Build | Score of an identical copy |
|---|---|
| 40×10 wall, one kind of brick | 0.67 |
| 20×20 floor, one kind | **0.55 (missed)** |
| 30×30 floor, two kinds in a checkerboard | **0.51 (missed)** |
| 12×12×6 solid block, one kind | 1.00 |

The cause is in `offsetsByVote()`. The anchors are the first 48 points of
*mine* by key **string**, so `x=10` sorts before `x=2` and the anchors
cluster at x = 0, 10 and 11. Each is paired with only the first 64 points of
the same kind in *theirs*, in placement order (x = 0 to 3 for the floor).
The true offset then gets 20 votes and a wrong one 28, and only the top
three offsets are tried. The score also depends on the order the bricks
were placed in. The score shown to the builder ("how
much is the same") is wrong as well: an exact copy of the wall reads 67%.

**Fixed** after this review: sampling is now by place and spread evenly, and
the corner offsets below are tried. The ready-made evaluation's report is
unchanged. **Suggested fix.** It is small and stays deterministic. For each turn,
also try the offset that lines up the two bounding boxes' minimum corners,
and the one that lines up their centroids. For any rigid copy, one of
those is exactly right. Also spread the 64 paired points across *theirs*
(take every n-th point) instead of the first 64. Add the four builds above
as tests.

### 2. High: a backdated `publishedAt` reverses which build came first

**Fixed** after this review, without anchors: their `anchoredAt` is only
the anchoring system's report until a proof verifier checks it. Each date
is now backed by when this device first saw the build
(`core/publication/PublicationOrder.js`,
`application/publication/PublicationFirstSeenLog.js`). A build only dated
earlier is listed as dated by its builder, with when this device first saw
it, and also on the original's own Explore card. The 🔔 tells of it as
"dated before yours", and Publish never asks a builder to credit a copy
dated before their own build.

`findEarlier()` and `findLater()` decide "before" from the publisher's own
signed `publishedAt`. Validation only checks that it is a date
(`DecentralizedPublication.js:121`). Someone who copies a build and signs
an earlier date:

- is listed on the **original's** page as "Similar builds published
  earlier", which credits the copy as the source;
- never triggers the original builder's 🔔, because the notifier only asks
  for the builder's builds published *before* the copy.

The codebase already holds better evidence and the finder ignores it:
`LocalPublicationCatalog` records `receivedAt` (when this device first saw
a build), and `anchoring/` verifies Bitcoin and Arweave timestamp proofs.

**Suggested fix.** Order by the earliest time that can be checked: a
verified anchor where one exists. Where it can't be checked, don't use
`publishedAt` alone to say who was first. When this device received the
original before the copy, but the copy claims an earlier date, show both
as "dated earlier by its publisher" rather than "published earlier".
Notify the builder either way.

### 3. High: plain, low-variety builds are flagged as look-alikes

**Fixed** after this review: shared bricks must be at least 20 of at least
four kinds (`MIN_SHARED_KINDS`). Weighting by rarity and "detail agreement"
were measured and dropped: they lost too many copies with edits.
`scripts/evaluate-look-alikes.mjs` now measures false hints. Plain shapes
went from 34% to 0%, and same-challenge tiny homes from 17% to 1%.

**Measured.** Two builds made independently, both hollow boxes of plain
cubes, were flagged:

| Pair | Score |
|---|---|
| 10×10×4 box vs 10×11×4 box | 0.61 (flagged) |
| 10×10×4 box vs 10×10×3 box | 0.75 (flagged) |

`MIN_COMPARED_BRICKS = 20` counts bricks, not information. A four-walled
cube house is the most common beginner build, and the weekly challenge
("a tiny home") makes many of them in the same week. Each false match now
reaches a real person through the 🔔 as "a build that looks like yours".
That is a small accusation, and it erodes the credit system's trust.

The ready-made evaluation measures how ready-made structures are detected.
**Nothing measures the false-positive rate of `SIMILAR_BUILD_THRESHOLD`
itself on generic shapes.**

**Suggested fix.** Weight each shared point by how informative its kind is,
for example −log of the kind's share among the bricks this device has seen,
or simply give plain cubes, halves and logs less weight. Require at least
three kinds among the shared bricks. Extend
`evaluate-ready-made-detection.mjs` with an E5 that measures false
positives on generated boxes, towers and floors at the shipped threshold.
Consider a higher bar for the 🔔 than for the passive build-page list.

### 4. Medium: copies that are extended or mirrored are missed

**Fixed** after this review: alignment tries mirrored orientations, and 85%
of the smaller build standing in the larger is pointed out too. Extended
copies went from 0% found to 99%, and mirrored copies from 46% to 99%.

**Measured** on a random 120-brick build:

| Change | Score |
|---|---|
| Moved, or turned a quarter turn | 1.00 |
| 30% of bricks deleted | 0.70 |
| 25% of bricks changed to another kind | 0.74 |
| Copy plus 40% bricks of their own | 0.71 |
| **Copy plus 70% bricks of their own** | **0.59 (missed)** |
| **Mirrored (x → −x)** | **0.08 (missed)** |

Jaccard punishes additions, but "copy it and add a garden" is the usual
uncredited remix. A mirror is one click away for anyone who wants to hide a
copy. Both are blind spots in the threat the feature exists for.

**Suggested fix.** Also compute *containment*, shared bricks over the
earlier build's distinct bricks, and flag when either measure passes. Use a
containment bar of about 0.85, together with finding 3's information
weighting. Add a reflected pass to `TURNS`, which makes 8 orientations
instead of 4. This roughly doubles the alignment cost, which the time
budget already bounds.

### 5. Medium: candidates are chosen by recency, not by likelihood

`_eligible()` keeps the **300 newest** publications. `_matching()` then
stops after **1.5 s** of wall-clock time, which includes awaited reads from
the content store. Original work that gets copied is usually older and
popular, so it is the first to fall outside the cap or the budget on a
device that knows many builds.

**Suggested fix.** Keep a small per-hash index of kind counts (the input to
`similarityUpperBound()`, a few hundred bytes for each build). Rank every
candidate by its upper bound before loading any bytes, then compare the
best ones within the budget.

### 6. Medium: voice has no accuracy harness, and quality is not checked per language

**Fixed** after this review. `scripts/evaluate-voice-commands.mjs` measures
voice per language, with the app's own hearing and reading, on recordings
of `scripts/voiceCommandPhrases.mjs` (synthetic ones from
`scripts/synthesize-voice-corpus.mjs`, or people's). On 576 synthetic
recordings with Whisper tiny:

- English got 68% right (78–89% with natural-sounding voices).
- Every other language got 26–39% right, mostly by doing nothing.

The wrong actions came mainly from a misheard part name falling back on the
selection, so spoken commands now act on the selection only when they say
so. The 9 wrong actions left in 576 don't change the build. Outside
English, the first ask says voice hears English best.

Whisper base got 49% right overall (English 93%, others 31–53%), but at
4.3 s a command instead of 2.1 s and about 107 MB instead of 70 MB. Voice
was then switched to Whisper base, on the owner's decision.

- The release notes give "12 of 13 commands" from a single synthesized-voice
  run. No script or recorded set can repeat that result, so a change to the
  model, the engine or a matching constant can't be measured.
- Voice is offered in all eight languages on Whisper **tiny**, whose
  multilingual accuracy is weakest in Japanese, Korean and Indonesian. In
  Japanese, Chinese and Korean, `nearestBySound()` and `fuzzyPlaceNamed()`
  are switched off on purpose, so those languages have no fallback when a
  word is misheard. Players in those languages will get much worse results,
  and the app doesn't tell them.

**Suggested fix.**

- Add `scripts/evaluate-voice-commands.mjs`. It takes a folder of short
  recordings, each labelled with its expected command and language, runs
  `prepareSpeech` → `SpeechRuntime` → the Editor or World matcher, and
  reports command accuracy, the abstain rate and the wrong-action rate per
  language. Seed it with a few volunteers per language. The wrong-action
  rate is the number to guard.
- Until there are numbers, label voice as English-first in the other
  languages' introductions, or measure `whisper-base` (about twice the
  download) for ja, ko and id.

### 7. Medium: a stuck transcription locks voice until reload

**Fixed** after this review, as suggested below, with a 30-second timeout
that ends the stuck worker.

`transcribe()` passes no generation limit, so Whisper may generate up to
its default of 448 tokens. On single-threaded WebAssembly, a repetition
loop, which tiny models are prone to on noise, can take many seconds.
During that time `toggle()` ignores every press in the `'working'` state,
and there is no timeout.

**Suggested fix.** Pass `max_new_tokens` of about 40 to the pipeline call
(commands are a few words). Put a timeout around `transcribe()` in
`useVoiceCommands.finish()` that shows `failed`. Let `turnOff()` during
`'working'` win over the late result, which today overwrites it.

### 8. Low: retrieval and parsing features have no relevance tests across languages

**Measured.** Ask the guide's top result was right for about 12 of 16
English questions. The misses were "how can I undo a mistake" (Undo and
redo came second), "my build disappeared", "is it free" (matched "Hands-free
movement") and "how do I make a video". That is a good result for a feature
with no model, but `GuideHelp.test.js`, `LibrarySearch.test.js` and
`PlainCommand.test.js` check the mechanics on small fixtures, not
relevance on the real guide and lexicons, in eight languages that
translators edit.

**Suggested fix.** Add golden sets: about 20 questions with their expected
section per language for the guide, and about 20 utterances with their
expected plan per language for plain commands. Run them in
`npm run test:node` as a floor (for example, top-2 hit rate ≥ 0.8), so a
change to a lexicon or a translation can't quietly break them.

### 9. Low: smaller voice items

- The consent gate is the `forkbuild.voice.enabled` flag alone.
  `SpeechWorkerClient.downloaded()` exists, but nothing calls it. If the
  browser evicts Cache Storage but keeps localStorage, the next V starts a
  70 MB download without asking again (with progress shown). On a metered
  phone, ask again when `downloaded()` is false.
- Model download progress adds up only the files reported so far, so the
  bar can jump back when a new file starts. The pinned file sizes are
  known, so use them as the total.
- `SpeechRuntime.remove()` during a load clears `_loading`, but the
  `pipeline()` already running still sets `_recognize` afterwards.
- The engine is `onnxruntime-web@1.31.0-dev…`, a nightly. This is forced:
  transformers.js 4.3.0 bundles that build, so it is not a local choice.
  Move to the first stable 1.31 when transformers.js does.

## Coherence

The parts fit together. `LibrarySearch.wordsFound()` and `fold()` are the
one matching layer for library search, plain commands and World voice
commands, and `GuideSearch` and `Transcript` reuse `fold()` and `wordsOf()`.
Typing a command and saying it run through the same `planPlainCommand()`.
One finder serves Publish, the build page, World View, the 🔔 and
Explore. Every feature is pure in `core/`, has I/O in `application/` and is
wired in `ui/`, and none of them sends a player's input anywhere. I found no
duplicated or conflicting logic.

What is missing is **evaluation as a practice**. Ready-made detection has a
measured, reproducible script and thresholds chosen from it. Nothing else
does. That matters most where a wrong answer reaches another person, which
is the 🔔.

## Suggested order

1. Finding 1 (the alignment fix and its tests): small, deterministic, and
   it fixes wrong numbers shown today.
2. Findings 3 and 4 together, with an E5 false-positive evaluation, before
   the 🔔 reaches more builders.
3. Finding 2: decide which time counts as "earlier", using anchors and
   `receivedAt`.
4. Finding 7: the cap and the timeout, a few lines.
5. Findings 6 and 8: the evaluation harnesses, then decide per language.
6. Findings 5 and 9 as follow-ups.

## Appendix: reproduction

Run from any directory with Node 22. The paths assume the repository is at
`/home/user/forkbuild`.

```js
// probe-similarity.mjs: identical and changed copies, and coincidences
import { buildShape, compareBuildShapes } from '/home/user/forkbuild/core/catalog/BuildSimilarity.js';
const b = (definitionId, x, y, z) => ({ definitionId, position: { x, y, z } });
const sim = (a, c) => compareBuildShapes(buildShape(a), buildShape(c)).similarity;
const grid = (w, d, h, kinds) => { const o = []; for (let x = 0; x < w; x++) for (let z = 0; z < d; z++) for (let y = 0; y < h; y++) o.push(b(kinds[(x + y + z) % kinds.length], x, y, z)); return o; };
const box = (w, d, h) => { const o = []; for (let x = 0; x < w; x++) for (let z = 0; z < d; z++) for (let y = 0; y < h; y++) if (x === 0 || z === 0 || x === w - 1 || z === d - 1) o.push(b('cube', x, y, z)); return o; };
const floor = grid(20, 20, 1, ['cube']);
console.log('identical 20x20 floor', sim(floor, floor));          // 0.55
const checker = grid(30, 30, 1, ['cube', 'half']);
console.log('identical 30x30 checker', sim(checker, checker));    // 0.51
console.log('independent boxes', sim(box(10, 10, 4), box(10, 10, 3))); // 0.75
const mirror = (a) => a.map((q) => b(q.definitionId, -q.position.x, q.position.y, q.position.z));
const house = box(8, 6, 4).map((q, i) => (i % 7 === 0 ? b('window', q.position.x, q.position.y, q.position.z) : q));
console.log('mirrored house', sim(house, mirror(house))); // 0.55, missed
```

Ask the guide was probed with `guideSections()`, `guideIndex()` and
`searchGuide()` over the chapters `docs/user/README.md` links to, using
English `help.ignoredWords`.
